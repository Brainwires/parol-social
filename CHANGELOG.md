## [Unreleased]

### Added — Connections that follow the network, calls that adapt (`parolnet-rtc`, `parolnet-app`, `parolnet-simnet`, `specs/PNP-011-calls.md`)
- **Every interface, IPv4 and IPv6.** A connection binds one socket per usable local address and announces each as a host candidate; every socket asks the STUN servers of its own family. Loopback and link-local addresses are left out, and an interface announces one IPv6 address per prefix: the temporary one the system itself uses, never the hardware-derived one beside it. A pinned address (`AppConfig::bind_ip`, the bot's `--bind`) is one socket as before. STUN binding requests carry a random transaction id (they were all zero).
- **A network change restarts ICE instead of tearing down.** The core watches the interface list (a poll every 2 s; a change counts once two polls agree) and, with a contact whose app says it can, restarts ICE in place: the data connection through a second `rtc_offer` / `rtc_answer`, the call through `reoffer` / `reanswer` inside the session. DTLS, SRTP and SCTP continue, on the old path until a new one is found. A restart that is not answered or finds no path in 15 s falls back to the rebuild that existed. The relay client is asked at once whether its socket still lives. The path shows "connecting" while a connection has no working pair.
- **Calls are renegotiated.** `AppHandle::set_call_video` adds video to an audio call and stops or resumes a camera's stream; the desktop's Camera button uses it (an audio call gets the button when the contact's app can add video). The web app and the PWA do not renegotiate: with them a call stays as it was set up and a camera that is off sends black, as before. They are told apart by feature names (`renegotiate` in the call's `offer` / `answer`, `ice-restart` in the data channel's identity frame) that old peers ignore.
- **The encoder follows the path.** Call connections run the engine's TWCC-driven congestion control; its estimate reaches the client as `MediaEvent::TargetBitrate` and the desktop sets libvpx's rate from it (`Vp8Encoder::set_bitrate`). Video is repaired over RTX (RFC 4588), and received audio is de-jittered in the driver before it reaches the playout buffer.
- **Connection quality.** `AppEvent::CallQuality` about once a second: round trip time, loss each way, bitrates, the estimate, the selected pair's candidate types. The desktop's call panel shows one line while the connection is weak (loss over 5%, a round trip over 400 ms, an estimate under 200 kbit/s) and nothing while it is fine.
- **`parolnet-simnet`** (test-only): an in-memory network with seeded loss, delay, jitter, reordering and a rate cap, on which `parolnet-rtc` runs unchanged in virtual time. The M1 simulation checks run there: call setup, renegotiation, ICE restart when a machine changes networks, the estimate on an open and a capped link, and the profiles 2% loss / 300 kbit/s cap / 100 ms jitter, each asserting no video freeze over 2 s and that at least 92% of the played audio is still the tone that was sent.
- **PNP-011 "1:1 Calls"** (`specs/PNP-011-calls.md`, 34 MUST / 8 SHOULD / 1 MAY, each with a conformance test): the call signals, setup, busy / reject and timeouts, the media session (DTLS-SRTP authenticated by the session that carries its descriptions, Opus, VP8, the candidate policy), renegotiation, ICE restart, adaptation and quality. PNP-007's call and media sections are marked superseded.
- Engine findings, reported to the fork and worked around here without patching it: a NACK retransmission without RTX is refused by SRTP's index-reuse check once transport-wide sequence numbers are written (so ParolNet negotiates RTX); the other congestion controller with its pacer was tried first and set aside (on a capped link its delay detector rarely fired, and audio queued behind video in the pacer).

### Security — Web app: encryption at rest, a passphrase lock, encrypted backup (`web/`, `crates/parolnet-crypto`, `crates/parolnet-wasm`)
- **Everything the web app keeps on a device is encrypted** (`docs/web-port/at-rest.md`). Until now the identity secret, the ratchet sessions, the pending pairing secret, the TURN password, contacts and history were plaintext rows in IndexedDB. Each row is now sealed with AES-256-GCM (a random nonce per write; the row's store and key as associated data, so rows cannot be swapped) under a key generated by WebCrypto as non-extractable and kept as a `CryptoKey` object. Text keys (peer ids, setting names) are stored as HMAC tags, and plaintext is padded to 128-byte steps. What stays readable: row counts, message ids and their order, which messages share a contact, row sizes to the nearest 128 bytes.
- **A database of the previous version is sealed in place at the first start**, in one transaction that verifies every row before it is written and refuses to run twice; nothing is asked of the person. The database is now version 2 (a `vault` store for the keys).
- **"Lock ParolNet with a passphrase"** (Settings, You): the storage keys are replaced by ones kept only under a key stretched from the passphrase with **Argon2id** (64 MiB, 3 passes; new `parolnet_crypto::kdf::argon2id`, RustCrypto `argon2` 0.6, exported from the wasm core and checked against OpenSSL's). An unlock screen at start, "Lock now", change and remove (both ask for the current passphrase), wrong tries counted across restarts with a growing wait, and a plain statement that a forgotten passphrase cannot be recovered (the unlock screen offers deleting everything). Setting, changing or removing the passphrase makes new keys and re-seals every row.
- **Honest limits, in the document and in the app:** without a passphrase the key lives in the same browser profile, so a copied profile is only partly protected, depending on the browser; the passphrase is what protects a seized device; nothing here protects against script running in the app's origin; browsers may keep deleted (earlier plaintext) rows in their files until they compact them.
- **"Back up this device" / "Restore from a backup"** (`docs/web-port/backup.md`): one file (`PNBACKUP`, format version 1) with the identity, contacts and their verification state, sessions and the person's own relay server, history only when asked, under AES-256-GCM with an Argon2id key from a passphrase typed twice; the header is authenticated. Saved through a link the person presses. Restore is offered on first run and in Settings (there after typing "replace"); it is checked in full before anything is written and replaces everything in one transaction. Settings shows the date of the last backup, and the list suggests one once there is a first contact. Sessions in a backup go stale as soon as the two devices talk again, so restored contacts are marked: the conversation says so, a failed connection check says "add each other again" instead of the general explanation, and the mark comes off once a connection has held.
- The desktop interop driver reads the web app's contacts and messages through its test hooks instead of its database, which is no longer readable.

### Fixed — Web app: "Turn camera off" no longer freezes the page in WebKit on Linux (`web/src/state/engine-store.ts`)
- **What was wrong:** in WebKit's GStreamer ports, taking a stream away from its `<video>` right after its camera track was disabled can block the page's main thread for good. "Turn camera off" did exactly that to the self view (6 freezes in 261 runs of the call flow).
- **Fix:** the store detaches the self view first and then has the engine switch the track off; the stream is allowed again before the track is switched back on. In the reproduction (`web/tests/e2e/repro`, new orders `camera-off-detach-first`, `camera-off-clone`, `camera-off-clone-keep`) the old order froze 15 of 20 pages and the new one 0 of 20; in the call flow 0 of 240 runs froze at the button. Showing the self view from a clone of the track also avoids the freeze and was not needed.
- The call flow no longer reports that freeze as an expected, skipped failure: a frozen page fails it.

### Security — a relay accepts a `register` answer only for the challenge it issued on that socket (PNP-001 §10.6 registration; relay server, both profiles)
- **What was wrong:** the relay sent `{"type":"challenge","nonce":…}` and kept no record of it. A `register` carrying `pubkey`, `signature` and `nonce` was accepted when the PeerId was the hash of the key and the signature verified over whatever nonce the frame carried. One `(pubkey, signature, nonce)` triple of a peer, seen once by any relay that peer registered with or by anyone who captured the frame, registered as that peer on any relay for ever: its signaling (`rtc_offer` / `rtc_answer` / `rtc_ice`) and presence could be taken over, so calls could be diverted or denied. Content stayed end-to-end encrypted, and the channel binding stops a diverted call from being intercepted.
- **Fix:** each socket remembers the one challenge it has outstanding (32 random bytes, answerable for 60 s, single use). A credentialed `register` is accepted only if its `nonce` is that challenge (compared in constant time), and the signature is checked over the relay's copy of it. Every credentialed `register` spends the challenge, whether it passes or not; one with no challenge outstanding, another nonce or an expired one gets the usual `{"type":"error","code":"register_failed"}` with no new challenge in the answer, so the client asks again with a plain `register`, which counts against the 4 `register` frames a socket may send (PNP-001-MUST-075). A plain `register` repeated before the answer gets the same nonce again (the legacy PWA sends two on boot). Nothing changes on the wire: the native client, the web engine, the legacy PWA and `parolnet-cli` all echo the relay's nonce already.
- **Not changed:** what the client signs is still the bare nonce, with no relay identity in it, so a relay a client connects to can pass another relay's fresh challenge to that client as its own and use the answer there, once, while the client is connecting. Closing that changes the signed message and PNP-001, and is left for a decision. `POST /tokens/issue` (relay profile) signs a nonce the client chooses and stays as it was: nothing is keyed on the identity presented there, so a replayed request obtains only what a new key obtains.

### Fixed — the scanner's pairing-code timestamp check has no gaps (PNP-003 §5.1, MUST-011; native app and web through `parolnet-wasm`)
- `parse_qr_payload` skipped the age check when `ts` was 0 and never refused a timestamp in the future, so a code could be made that a scanner accepts for ever. A code is now refused when its `ts` is more than 30 minutes behind the scanner's clock (0 included) or more than 30 minutes ahead of the scanner's current 5-minute bucket: a presenter's clock may run up to half an hour fast. `parse_qr_payload_at` takes the time as an argument. Codes the core generates are unaffected; the payload format is unchanged. The web engine's own checks (`web/src/engine`) already agree on the past bound and need no change.

### Security — an authority endorsement no longer carries over to a forged relay descriptor (PNP-008 §6.3, MUST-027 / MUST-028 / MUST-030; relay profile, `parolnet-wasm`)
- **What was wrong:** an endorsement signs the relay's PeerId and a validity window, and `EndorsedDescriptor::verify_threshold` checked nothing about the descriptor but that PeerId: not the relay's signature, not that the PeerId is the hash of the identity key. Anyone could attach a relay's (public) endorsements to a descriptor with their own keys and address and `POST /endorse` it; the relay then listed the attacker under the endorsed relay's PeerId. The unendorsed path (`/directory/push`, `handle_gossip_descriptor`) verified the signature against whatever key the descriptor carried, so a self-signed descriptor could claim any PeerId there too.
- **Fix:** `RelayDescriptor::verify_self_signature` (PeerId is the hash of `identity_key`, and that key signed the descriptor) gates both paths, in `parolnet-relay` and in the `parolnet-wasm` mirror behind `verify_endorsed_descriptor`. `verify_threshold` also refuses a descriptor older than seven days (MUST-027 item 3), and `handle_endorsed_descriptor` keeps the descriptor it has when the one offered is not newer (MUST-030), so an old descriptor cannot be brought back under a still-valid endorsement.
- **Not changed:** what an endorsement signs. PNP-008-MUST-002 has it cover the descriptor itself; it still covers the PeerId only, so the holder of an endorsed relay's identity key can change that relay's address and onion key without a new endorsement. Closing that changes the endorsement format, the authority CLI and how often authorities sign, and is left for a decision. The legacy PWA's own JavaScript check (`pwa/relay-client.js`) is unchanged as well.

### Security — group operations can be signed and are verified before they apply (PNP-009 §6.1, §6.3, §6.4: MUST-019 to MUST-024, MUST-071)
- `GroupOperation` had a `signature` field nothing filled or checked, and the core had no way to apply a received operation at all. New: `GroupOperation::signable_bytes` (the CBOR of the §6.2 map, `signature` a zero-length byte string), `sign` and `verify_signature`, and `GroupManager::apply_operation`, which applies an operation only when we are in the group, its version is above the group's, `admin_peer_id` is a current admin and the signature verifies under the Ed25519 key that PeerId is the hash of. A refused operation changes nothing. A removal or a `rotate_keys` returns our new sender-key distribution for the caller to send.
- `GroupManager::remove_member` let the only admin remove itself, leaving a group nobody could administer. That and demoting the last admin are refused (MUST-019).
- Not wired to a transport: no shipped client sends or receives `GroupOperation` (the native app and the web app have no groups; the legacy PWA manages membership with its own unsigned `invite` message in JavaScript, which this does not change). `add_member` / `remove_member` still return the operation unsigned for the holder of the identity key to sign. The struct's `timestamp` is not a field of the spec's map and is not signed.

### Fixed — Double Ratchet: the send counter cannot wrap and `encrypt` zeroizes its message key (`parolnet-crypto`)
- `DoubleRatchetSession::encrypt` returns an error when `send_n` is `u32::MAX` in place of overflowing (a panic in debug builds; in release message number 0 again in the same chain, so two messages with one `(ratchet_key, message_number)`). The check comes before the chain key moves: a refused encrypt changes nothing, and the chain is usable again after the peer's next ratchet key. `decrypt` refuses a header with message number `u32::MAX` before it does anything else, where `recv_n + 1` overflowed ahead of the AEAD check. No spec text changes; the limit is not yet a clause of PNP-002.
- `encrypt` held its message key in a plain array that was never erased, on success and on every error path. It is zeroized on drop now, as `decrypt`'s already was (security invariant 2).

### Fixed — the sender-key chain index cannot wrap (`parolnet-crypto`)
- `SenderKeyState::encrypt` returns an error when the chain index is `u32::MAX` in place of overflowing (a panic in debug builds, a wrapped index in release), and `decrypt` refuses a message claiming index `u32::MAX`, which would have wrapped the receiver's index the same way. A failed encrypt at the limit changes nothing; the sender has to rotate.

### Security — sender-key rotation replaces the signing key pair (PNP-009 §7.2, MUST-029)
- `SenderKeyState::rotate` replaced the chain key and reset the index but kept the Ed25519 signing key, against PNP-009-MUST-029. Every member holds a sender's chain key, so the signature is all that stops one member writing as another: a signing key that had leaked stayed good for forging after the rotation that was supposed to answer the leak (MUST-027). Rotation now generates a new pair; the distribution built afterwards carries the new verification key, as it always carried the current one, and the old private key zeroizes when dropped. Nothing changes on the wire. A receiver still holding the pre-rotation state now fails the signature check on the new chain, where it used to fail the AEAD check.

### Security — comparisons of authenticators are constant-time (security invariant 5; PNP-007-MUST-062, PNP-009-MUST-069)
- `FileTransferReceiver::assemble` and `GroupFileReceiver::assemble` compared the SHA-256 of a received file with `!=`; they use `subtle` now. The conformance tests for the two clauses did their own `subtle` comparison and passed either way; new ones pin the implementation.
- The relay's `ADMIN_TOKEN` check (`/peers`, every profile) compared the bearer token with `==`. It compares SHA-256 digests of the two in constant time, which also hides the configured token's length.
- LAN discovery's 8-byte HMAC tag (`parolnet-mesh`) and the channel-binding fingerprint lists (`ChannelBinding::verify`) are compared with `subtle` too. Neither is known to have been exploitable: the tag check is not reachable from a shipped binary, and DTLS fingerprints are not secret.

### Fixed — forwarded gossip verifies after the first hop (PNP-005 §3.1, §5.2; `parolnet-mesh`, relay profile only)
- The originator's signature covers `ttl` (PNP-005-MUST-003) and every hop decrements it (PNP-005-MUST-020), so `StandardGossip::process_gossip` refused every message at its second hop with "invalid Ed25519 signature". A receiver now verifies over the originator's `ttl`, which is `ttl + hops` (`GossipEnvelope::origin_signable_bytes`); a sum above the maximum `ttl` is refused. What an originator signs is unchanged, so nothing changes on the wire. A forwarder can no longer hand a message more hops than its originator signed for.

### Fixed — Web app: hanging up no longer freezes the page in WebKit on Linux (`web/src/engine/calls.ts`, `web/src/platform/playback.ts`)
- **What was wrong:** in WebKit's GStreamer ports (WPE, WebKitGTK: GNOME Web, and what CI runs as "WebKit") `RTCPeerConnection.close()` and `MediaStreamTrack.stop()` can block the main thread for good when a `<video>` is still playing the stream whose track they end. The engine closed the call's connection and stopped the capture before the call screen had let go of the streams, so the page of either person could freeze at hang-up: 6 of 36 runs of the call flow on a busy machine, and the `pwa-interop` job's "real flows" step in CI. `web/tests/e2e/repro` shows the browser defect with no app code (11 of 30 pages) and the order that avoids it (0 of 30).
- **Fix:** the end of a call is published first; in that same turn the store detaches every `<video>` of the call (`StoreEnv.keepPlaying`, a registry of the call's elements); the engine then stops the capture and closes the connection in tasks of their own, each guarded, with a log line before each browser call. Nothing waits for that release: a release that fails or never returns keeps neither the ended state nor the next call waiting. Switching cameras announces the new capture before the old one is stopped, the same way. In 156 runs of the call flow on the final code no page froze at hang-up.
- **Not fixed:** a second way the same browser freezes a page, when a stream is detached from its element right after its camera track was switched off. That is "Turn camera off" (3 of those 156 runs); the app does there what it did before. The call flow reports exactly that freeze as skipped, with its reason, and fails on anything else. `docs/web-port/app.md` ("Browsers", "Owed") has both, and says that Safari on macOS and iOS is untested.
- Tests: the engine's order of teardown (ended before released; a release that throws; a next call before the release ran), the store and the element registry; the call flow now checks on both pages that the capture is stopped and the connection closed after hang-up, and a failure says whether a page's main thread is blocked.

### Security — the whole Double Ratchet header is authenticated (PNP-002 v0.6 §5.7, MUST-042; PNP-001 v0.14 §3.3) — BREAKING on the wire
- **What was wrong:** the session AEAD's associated data was `ratchet_key || extra_aad`. `message_number` was bound only through the nonce and `previous_chain_length` was bound to nothing, although the receiver acts on it before it can check the tag.
- **Impact:** whoever relayed the genuine first message of a new sending chain could rewrite `previous_chain_length` and the message still authenticated. Raised, the receiver derived and stored up to 1000 skipped keys for messages that were never sent; lowered, the receiver closed the previous chain early and its late messages could never be decrypted. No key or plaintext was exposed and no forged content was accepted.
- **Fix:** the associated data is now `ratchet_key (32) || previous_chain_length (u32 big-endian) || message_number (u32 big-endian) || extra_aad`, on encrypt and on decrypt, the skipped-key path included. The nonce, the key derivations and the stored session format are unchanged. A message with an altered header fails authentication and, with the all-or-nothing receive below, leaves the session as it was.
- **Breaking:** wire-incompatible with every earlier build: a message from one side of the change does not decrypt on the other. The native core and the WASM client are built from the same crates and ship together; no version field is bumped and nothing is negotiated (the specs define no envelope-version negotiation, and nothing is deployed that would need it). Messages in flight across the upgrade are lost; sessions themselves carry over.
- **Spec and tests:** **PNP-002-MUST-042**, PNP-001-MUST-007 restated; `pnp_002_double_ratchet.rs` and unit tests alter each header field in transit, on a new chain and on a message read through a skipped key.

### Security — skipped message keys are bounded and evicted (PNP-002 v0.6 §5.8, MUST-043 / MUST-044)
- **What was wrong:** skipped message keys left a session only when their messages arrived, and the limit of 1000 counted the keys already stored. A session that had accumulated 1000 keys of messages that never came refused every later out-of-order message, for good.
- **Fix:** one received message may make the receiver derive at most 1000 keys (`MAX_SKIP`, the work bound before authentication; stored keys no longer count), and a session stores at most 2000 (`MAX_STORED_SKIPPED`); when it is full the oldest stored key is deleted first, in the commit that follows a successful authentication, so a forged message evicts nothing. Used and evicted keys are zeroized where they lie in the store.
- The persisted session keeps its format (version byte `0x01`): the skipped keys are now written oldest first and that order is the eviction order. A session stored by an earlier build loads; its skipped keys are taken in the order found.

### Security — sender-key decrypt is all-or-nothing
- `SenderKeyState::decrypt` (and `GroupManager::decrypt_group_text` through it) removed the skipped key it was about to try and advanced the chain before the AEAD check. The Ed25519 signature gates this, but it proves the sender, not the chain: a validly signed message of another chain of the same sender (after `rotate`, which keeps the signing key) consumed keys of the chain the receiver held and moved it forward. The receive now works on a copy and commits after the tag verifies, as the Double Ratchet does. This corrects the note below that found the sender keys sound.

### Fixed
- `parolnet-app`: the relay reconnect backoff starts over as soon as a socket got registered, however that socket ends. Before, only a clean close reset it, so a long-lived client whose sockets ended in errors or by the 40 s silence limit drifted to the 30 s maximum.
- `parolnet-core`: `SessionManager::peer_ids()`. `trial_decrypt` (WASM) and the CLI listed the peers through `export_all()`, which serialized every session's keys into buffers that were never zeroized.

### Security — Double Ratchet decrypt is all-or-nothing (PNP-002 v0.5 §5.7, MUST-041)
- **What was wrong:** `DoubleRatchetSession::decrypt` changed the session before the AEAD tag of the message was checked, and kept the changes when the check failed. It consumed the skipped message key it was about to try, performed the DH ratchet step for whatever ratchet key the header carried (replacing the remote key, the root key, both chain keys and our sending ratchet key), stored skipped keys up to whatever message number the header claimed, and advanced the receiving chain.
- **Impact:** denial of service on a session. One envelope that did not authenticate (forged, corrupted in transit, or simply addressed to another session and tried against this one) left the two ends unable to decrypt each other, permanently, with a new pairing as the only recovery. Anyone able to deliver one envelope to a session could do it: a relay, a third device, a peer connected under a contact's PeerId before the channel binding (PNP-001 §10.5.1) is verified. The sealed-sender trial decrypt (`trial_decrypt`, which tries an envelope against every session) made one stray envelope damage every session of the client. No confidentiality or integrity impact: no key or plaintext was exposed and no forged message was ever accepted.
- **Affected:** every user of `parolnet-crypto`'s Double Ratchet: the native core (`parolnet-core`, `parolnet-app`, the desktop client, `parolnet-cli`) and the WASM bindings / PWA (`envelope_decode`, `trial_decrypt`).
- **Fix:** a receive runs on a working copy (root key, chain keys, counters, the new ratchet secret of a DH step, the skipped keys the message derives) that is written back only after the tag verifies and is zeroized when it is dropped. The stored skipped keys are not copied, a skipped key is removed only by the message that authenticates under it, and the skipped-key limit counts stored plus pending keys, so a failed call can neither grow nor shrink the store. Wire format, key derivations and the output of a successful decrypt are unchanged; sessions stored before the fix load as they are. A session already damaged this way is not repaired by the fix.
- **Spec and tests:** PNP-002 v0.5 adds §5.7 and **PNP-002-MUST-041** (a receiver MUST NOT change session state for a message that fails authentication), pinned by `crates/parolnet-conformance/tests/pnp_002_double_ratchet.rs`. Regression tests in `parolnet-crypto` (random ciphertext, unknown ratchet key, message numbers inside and past the skip limit, replays, a tampered message for a skipped key, and garbage interleaved with out-of-order genuine traffic in both directions), in `parolnet-core` (an envelope of a third identity, trial decrypt across sessions, a bootstrap envelope that does not authenticate) and in `parolnet-wasm`.
- Reviewed with the same question and found sound: the pairing bootstrap (`try_bootstrap_and_decrypt` commits its candidate session only after the tag verifies, PNP-001-MUST-064) and group sender keys (the Ed25519 signature of the sender is verified before any state changes).

### Security — Encrypted storage on the desktop (`parolnet-store`, M1 third slice)
- New crate `parolnet-store`: the identity secret, contacts, Double Ratchet sessions, chat history, the sender queue and settings live in one SQLite database encrypted page by page with SQLCipher (`rusqlite`, bundled). The 256-bit database key is random, made on first run and held by a `KeyProvider`: the OS keychain (`keyring`: macOS Keychain, Windows Credential Manager, Secret Service on Linux; cargo feature `keychain`), an owner-only key file in the data directory for machines without a keychain service (headless Linux, CI, the bot; it does not protect a copied directory or a seized disk), or memory (tests). A store records the kind of provider it was created with and refuses to open with another, so nothing moves from the keychain to a file by itself; a store whose key is gone is reported, not recreated.
- The identity key and the ratchet state are no longer plaintext files. A data directory from the earlier slices (`identity.key`, `state.json`) is imported on first open in one transaction, read back, and only then are the plaintext files overwritten and removed (the identity last); an interrupted cleanup finishes on the next open and a failed import removes nothing.
- Schema with a version table and forward migrations; tables for key-value data (identity, settings), contacts, sessions, messages (by contact and id) and the queue. Writes are incremental and transactional (WAL, `synchronous=FULL`, `secure_delete`): sending a message writes that message, the session that ratcheted and the queue row, not the whole state. `parolnet-app` hands the rows to a dedicated writer thread, so the engine's task never waits for a commit; shutdown waits for the last one. One instance per data directory (the database is locked exclusively).
- "Delete all data on this device": `parolnet_app::delete_all_data` (`parolnet_store::wipe`) removes the key from its provider, then the database files and any leftover plaintext.
- `AppConfig::key_storage` (`KeyStorage::File` by default; the desktop app sets `Keychain`; `Provider(..)` injects one). The desktop gets `--key-storage keychain|file`; the bot and `--call-check` use the key file.
- SQLCipher's cipher is a C library: CommonCrypto on Apple systems, a statically linked OpenSSL libcrypto built from source elsewhere (the build needs perl and make, on Windows a native perl such as Strawberry Perl and nmake). This is encryption of local storage, outside the end-to-end layer, whose primitives stay pure Rust. `cargo-deny`: `sqlcipher-src` is allowed its public-domain `blessing` / `WTFPL` terms by a named exception in both `deny.toml` files.

### Fixed — contacts stuck "offline" after `peer_offline` (PNP-001 v0.13 §10.5, SHOULD-019)
- The relay pushes presence only between mutual watchers (and for at most 256 watched ids). A contact known to be offline only from the `peer_offline` answer to an offer was never offered to again unless messages were queued for it, and then only every five minutes: a freshly paired contact, one beyond the watch limit, or a missed push stayed "offline" until the user pressed Retry. That verdict is provisional now: the contact is offered to again after about 15 s, doubling to 5 min (queued messages, or the user asked to connect) or 15 min (otherwise), with jitter, whether or not anything is queued. A presence push, an offer or answer from the contact, or an open channel ends it; Retry / opening the chat offers at once and starts the backoff over. All probes share a budget (12, plus one a minute: at most 72 an hour against the relay's 240) and wait out `rate_limited`. A contact a presence push called offline is not probed, as before. Probes are quiet: the contact stays "offline" in the UI until it answers. The schedule is `parolnet_app::reconnect` (pure, unit-tested); the intervals are `AppConfig::reconnect`.

### Removed — Per-identity token issuance rate limit (PNP-001 v0.8)
- Dropped the `/tokens/issue` per-(identity, epoch) budget cap from the relay-server. Operationally it was gating legitimate browser reloads faster than it was stopping abuse: identity creation is free in PNP-002 (Ed25519 keygen, no registration), so an attacker just rotates identities and the cap never touches them. Meanwhile any user with a persistent browser identity could exhaust the budget across a handful of page loads. The per-frame defenses that actually matter — MUST-050 per-epoch spent-set (replay protection) and MUST-052 Ed25519 signature gate at issuance — stand on their own without the cap; network-layer abuse is the job of fail2ban on the deployment host.
- **PNP-001 v0.8:** the §10.2 clause relaxes from `MUST-063` (cumulative cap REQUIRED) to `MAY-005` (cumulative cap OPTIONAL). The MAY form retains the exact accounting shape a re-enabled implementation must use (running total, 429 without advance, epoch-reset) so interop stays stable if abuse telemetry later justifies turning it back on. MUST count drops 63 → 62.
- Relay-server: the `IssueLimiter` type is kept as a unit-typed placeholder so a future re-enable doesn't touch the handler signature. The 429 branch is gone.
- PWA: `DEFAULT_BATCH_SIZE` goes from 256 back up to 1024 now that the per-epoch cap is no longer a constraint — fewer round-trips without any abuse-control downside. `LOW_WATER` rises to 128 to match.
- Conformance: MUST-063 test retagged as the MAY-005 shape-conformance test — a relay that does re-enable the limiter has a pin to target. Workspace: 1253/1253 green.

### Changed — Spec/code drift cleanup: token-issuance accounting + federation admission
- **PNP-001 v0.7:** Added `PNP-001-MUST-063` to §10.2 making the `budget_per_epoch` cap explicitly cumulative per (identity, epoch). ### Security — Phase 1-3 Audit Fixes

- TLS stream: `MAX_FRAME_SIZE` (64 KiB) guard on `recv()`
- CBOR codec: `MAX_HEADER_SIZE` (512 B) guard before decode
- Gossip: `MAX_ENVELOPE_SIZE` + `is_valid_structure()` on inbound envelopes

### Breaking Changes
- `PaddingStrategy::pad()` signature changed from `Vec<u8>` to `Result<Vec<u8>, PaddingError>`
- `hkdf_sha256` return type changed from `Result<Vec<u8>>` to `Result<Zeroizing<Vec<u8>>>`
- EXTEND cell format changed from `SocketAddr` to `PeerId`
- Relay CREATED cell now includes HMAC field (32 bytes)
- Gossip `signable_bytes()` no longer includes `hops` and `seen` fields — existing signatures incompatible
