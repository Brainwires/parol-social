# PNP-006 Traffic Shaping: conformance, clause by clause

State of the branch `test/conf-pnp-006`. The first version of this file was a read-only audit of commit d8ceedb that found 6 of 45 MUST and 0 of 15 SHOULD clauses with a real test; most of the others were pinned to tests that asserted constants. Those tests are gone. Each clause below now either has a test that runs the production code and fails when the behaviour is removed, or has no test and says why.

Test files (all in `crates/parolnet-conformance/tests/`): `shape` = `pnp_006_traffic_shaping.rs`, `direct` = `pnp_006_direct_path.rs`, `tls` = `pnp_006_tls.rs`, `dc` = `pnp_001_direct_channel.rs`, `sig` = `pnp_001_signaling_only.rs`.

Where the code lives:

- `parolnet_protocol::shaping`: bandwidth modes, the send scheduler, traffic profiles (sans-I/O, shared by every sender).
- `parolnet_relay::shaped`: cover traffic on a circuit. Library only: the default clients do not use circuits.
- `parolnet_transport::tls_stream`, `tls_camouflage`, `conn_manager`: the TLS transport (HTTP/2), fingerprint profiles, connection keeping. Library only.
- `parolnet_app` (`engine.rs`, `signaling.rs`, `relay_socket.rs`): what the shipped native client does.
- `web/src/engine`: what the shipped web client does.

## Without a test

- **MUST-028, MUST-029, MUST-030, MUST-044** (a ClientHello that matches a browser's, a TLS library with fine-grained ClientHello control, an observer who sees a browser). rustls builds the ClientHello itself: the extension set and order, GREASE, the signature algorithm list and the padding extension cannot be set, and suites and groups it does not implement cannot be offered. No maintained, permissively licensed Rust TLS library offers that control; the alternative is a patched BoringSSL (C and C++, built with cmake), which is a dependency decision for the project and not something a conformance pass should make. What a profile can decide (cipher order, group order, ALPN, SNI) is applied and tested under MUST-031. In the web client the ClientHello is the browser's own.
- **MUST-039, SHOULD-005** (profiles updated every six months, targeting the latest stable browsers). The built-in profiles were written down from knowledge of Chrome 131 and Firefox 132, not captured from a running browser, and nothing here could check them against one. A date on them would claim more than is known. They also describe a ClientHello the code cannot send (above).
- **MUST-034, SHOULD-009** (relay nodes listen on port 443). The relay binary speaks cleartext HTTP and is meant to sit behind a TLS front (the image's nginx listens on 80, behind the operator's terminator). Its own port (default 9000) is not the port a client sees; making 443 the default would put cleartext on 443 and collide with a TLS front on the same host. The port of a deployment is its operator's configuration.
- **SHOULD-011** (profile bundles distributed by gossip). No spec defines a gossip payload for a profile bundle. It needs a wire format in PNP-005 first.

## Notes

- **The padding interval and the jitter.** §3 and the figure in §4.1 call the padding interval the maximum time between two sends; MUST-006, -018 and -019 add a jitter of 0 to J_max to it. The code follows the numbered clauses: a gap is the interval plus the jitter.
- **Where the dummy flag sits.** §4.3.4 puts the flag in the first byte of "the decrypted inner payload"; PNP-004 §3.7 puts the Stream ID at offset 0 of a DATA payload. The code reads the two together: the flag is the first byte of the §3.7 Data bytes, which is what the exit relay delivers and `shaped::open_inner` reads.
- **One sender per circuit.** A circuit from `StandardCircuitBuilder` pads itself when idle (PNP-004 §5.9). `ShapedCircuit` stops that task and sends every cell of the circuit itself, through the circuit's own send path (same counters, same counter limit). A relay fills in for a silent neighbour only after one and a half intervals, more than the interval plus the largest jitter of any mode, so it does not double a shaped circuit's cells.
- **When a message counts as sent (native client).** A message stays in the stored queue until the contact's SCTP has acknowledged it; a slot hands it to the channel, the acknowledgement removes it and marks it `Sent`. `pnp_005_sender_queue.rs` `messages_given_to_a_dying_channel_stay_queued_and_arrive_over_the_next` shows it with pacing on.
- **Market share and the 50 % cap.** SHOULD-010 (draw by market share) and SHOULD-013 (no fingerprint over half) disagree whenever one engine has more than half the market, which Chromium has. The cap wins; the excess goes to the other fingerprints in proportion.
- **MUST-041 and the default relay.** The signaling-only relay (PNP-001 §10.5) speaks its registration protocol to whoever opens `/ws` and refuses every cell (MUST-045), so "nothing until a valid CREATE cell" cannot apply to it. The clause is implemented for the relay-profile listener.

## Remaining

- **The web client does not pace** (MUST-007, -008, -009, -018 to -021 in the browser) and has no bandwidth modes (MUST-001, -002, -042). Its engine is a separate TypeScript implementation; porting the send slots touches its queue, its delivery states and most of its engine tests. Interoperation is unaffected: pacing changes when a client sends, not what.
- **No control for the bandwidth mode** in the desktop or web UI; the native core has the API and emits the warning as a notice.
- **The native client does not rotate its relay connection** after 1 to 4 hours (SHOULD-001). With the 30-second wait of MUST-024 a rotation would take the client off its relay for half a minute every few hours and flap its presence for every contact.
- **The clients' relay socket is a WebSocket over HTTP/1.1** (MUST-035 to -037 as far as that socket goes): tungstenite speaks HTTP/1.1, and a browser chooses its own.
- **The relay server's own circuit handling** (the opt-in relay profile's single-relay exit) does not use `ShapedCircuit` or the flagged DATA payload. The legacy PWA, which had the only circuit client, was removed; the web app has none.
- **Gossip connections carry no dummy gossip messages** (the second half of MUST-004, and the gossip half of §4.3.3). `parolnet-mesh` has no send schedule, and PNP-005 does not say whom a dummy USER_MESSAGE is addressed to or where it stops; that needs spec text in PNP-005 first.
- **Envelope-level decoys would be visible to a relay.** The legacy PWA (removed) sent cover envelopes whose `msg_type` DECOY (0x04) is in the cleartext header PNP-001 defines; the web app and the native client send none and drop the ones they receive. A relay that carried such envelopes could tell them from real ones, against MUST-013 / MUST-015. The circuit dummies of this branch do not have that problem; envelope-level ones cannot lose it without a change to PNP-001's header.
